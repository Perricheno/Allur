# Журнал, оперативные паспорта и архив сети

## Интерфейс

- Журнал: событие показывается при пересечении его времени, без прежнего пятисекундного кэша. Стабильные идентификаторы сохраняют раскрытые объяснения и фокус. Новые записи появляются с короткой анимацией в голубой гамме. `prefers-reduced-motion` отключает движение. «Пауза ленты» фиксирует только чтение, не общие часы.
- Поезда: нажать номер. Паспорт включает все поля характеристик, состояние, причину остановки, прогноз продолжения, координаты, прогресс, полный список остановок и недавние события рейса. Обновление раз в секунду.
- Станции: нажать название. Карточка показывает привязку, связанные маршруты, стоящие поезда, операции и причины, будущие прибытия активных рейсов, соседние поезда и события. Нахождение рядом не считается занятостью станции. На узловой станции учитываются маршруты с совпадающим названием остановки, а не только ближайшая линия.
- Статистика: «За всё время» по умолчанию. Обновление до четырёх раз в секунду и серверные сообщения архива. История открывается целиком или по типу операции нажатием числа в таблице. Разбор содержит основание, длительность и формулу эффекта, когда она предусмотрена моделью.

## Что означает «за всё время»

Сервер хранит append-only `network-events.jsonl` рядом с файлом `KTZ_STATE`. При первой установке восстанавливается предыдущие 24 часа по текущему расписанию; затем новые записи дописываются без удаления старых. Начало архива явно показывается на экране. Старые версии расписания до установки архива восстановить нельзя.

Перезапуск не сбрасывает архив. После простоя сервер достраивает пропущенный интервал дневными порциями, идентификаторы предотвращают дубли. Возврат модельного времени назад скрывает будущие записи, но не удаляет их с диска. В тестовом режиме архив только в памяти. Ошибка чтения архива не выключает движение: API архива отвечает 503, интерфейс сообщает о неполноте истории. JSONL необходимо включить в резервное копирование вместе с `state.json`.

## API и экспорт

- `GET /api/network-events`: SSE, начальное сообщение `archive`, далее `batch` при появлении записей. Сервер проверяет ход модели каждую секунду; интерфейс дополняет поток событиями точного локального модельного времени между серверными тактами.
- `GET /api/network-export?section=all|trains|stations|model|decisions|journal`: JSON-снимок с версией схемы, реальным временем экспорта и временем модели. Экспорт не ограничен фильтрами и пагинацией экрана.
- `trains`: все активные рейсы, полные характеристики и прогноз остановок.
- `stations`: исходный каталог OSM, индексы, текущие операции, ожидаемые прибытия и соседние поезда для всех станций.
- `model`: маршруты, службы расписания, сводка сети и снимок детальной диспетчерской модели.
- `decisions`: текущие варианты и объяснения плюс весь архив операций.
- `journal`: все сохранённые события до времени снимка, причины и доступные формулы экономии.

Показатель общего числа решений включает операционные события — отправления, приёмы, смены бригад, задержки, пропуски и разрешения. Это не число запусков оптимизатора. Расчёт экономии при пропуске и смене бригады сохраняет существующие формулы модели, а не измеряет причинный эффект по фактическим альтернативным рейсам. Для остальных событий экономия не придумывается.

## Проверка

`npm run check`, `npm test`, `npx playwright test e2e/network-live.spec.js`.

Покрыты точные временные границы, откат часов, уникальные события, соответствие паспорта профилю рейса, отделение близости от стоянки, восстановление архива, мобильная ширина, возврат фокуса, стабильность строк, пауза ленты, все разделы JSON и скачивание файла.

## Ограничения роста

Архив хранится на сервере без ограничения по сроку, но текущая реализация загружает его в память и отправляет браузеру целиком. Для длительной промышленной эксплуатации нужны серверная пагинация, агрегаты и потоковый экспорт. Для текущего демонстрационного объёма десятков тысяч записей сохраняется доступ к каждой записи.

## Расписания и экономика

`/#/schedules`: планирование заявок на 6/12/24 часа. Заявки берутся из существующего непрерывного графика. Пул тяги — локомотивы действующих рейсов после прогнозного прибытия и оборота плюс явно настроенный резерв на станцию/вид тяги. Назначение целому составу проверяет местоположение, время готовности, вид тяги, пассажирское/грузовое назначение и заданный предел массы. Один локомотив не используется одновременно дважды; подготовка и оборот включены в интервалы занятости.

База — очередь готовности тяги. Кандидат — раннее отправление и ближайшее время готовности. Если кандидат теряет назначенный базой рейс или ухудшает взвешенный простой, остаётся база. Это эвристика, а не глобальный оптимум. Нет подходящего локомотива — явная необеспеченная заявка, а не удаление рейса.

`GET/POST /api/schedule`: общий сохранённый план и ставки, файл `network-schedule.json` рядом с состоянием. Сервер пересчитывает присланные настройки, а не принимает произвольную клиентскую таблицу. План можно выгрузить в CSV/JSON; он также входит в полный экспорт модели.

**Граница исполнения:** сохранённый план не переписывает действующий генератор движения сети. Это планировщик назначений для последующего диспетчерского исполнения. В нём ещё нет полной проверки блок-участков, станционных маршрутов, тяговых расчётов профиля, ТО и допусков бригад. Параметры 45/20/10 минут и предельные массы — настройки сценария, не нормативы КТЖ.

Деньги и энергия — ожидаемый эффект сравнительного плана. Тарифы и расход по умолчанию не заданы. Летний, зимний и арктический дизель выбираются как альтернативные сценарии; электроэнергия в кВт·ч отдельно. Расход учитывает только разницу стоянок назначенной тяги, при предположении указанного режима потребления; ожидание вагонов без тяги не потребляет её топливо. Неиспользованный резерв, расход в движении и рекуперация отдельно не оценены. Отрицательный эффект не обрезается. Локомотиво-час и вагоно-час вводятся без уже учтённой энергии во избежание двойного счёта.

Задание на нормативную базу: `research/GEMINI_RESEARCH_BRIEF.md`.
